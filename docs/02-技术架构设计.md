## 1. 技术栈选型

| 层 | 技术选型 | 选型理由 |
|----|---------|---------|
| 后端框架 | Python 3.11 + FastAPI | 适合数据/AI 场景，异步高性能，后续接预测算法与 LLM 友好 |
| 前端框架 | React 18 + TypeScript + Vite | 工作台交互复杂，组件化生态成熟，类型安全 |
| UI 组件库 | Ant Design 5.x | 中后台管理场景成熟，表格/表单/图表组件丰富 |
| 数据库 | PostgreSQL 15（开发期可用 SQLite） | 关系型存储订单/任务/配置，支持事务与复杂查询 |
| ORM | SQLAlchemy 2.0 + Alembic | 主流 ORM，迁移管理成熟 |
| 定时调度 | APScheduler | 轻量单机调度，满足凌晨跑批需求；后续可换 Celery |
| 图表 | ECharts（前端） | 大盘可视化 |
| LLM 接入 | Provider 抽象层（Claude / OpenAI 兼容） | 可切换，MVP 可接真实 API 或 mock |
| 认证 | JWT | 轻量，前后端分离友好 |
| 部署 | Docker Compose | 单机起步，后续可迁移 K8s |

### 4.2 任务调度架构

#### 4.2.1 每日跑批流程

```
APScheduler (cron: 0 0 * * *)
   │
   ▼
[daily_batch job]
   │
   ├─ 1. fetch_orders()      # 拉取/读取订单与特征（CSV 已入库则跳过）
   ├─ 2. calc_risk()         # 对未计算订单算风险概率 → 写 risk_prob
   ├─ 3. map_risk_tier()     # 按 active risk_config 映射风险档
   ├─ 4. generate_tasks()    # 核心调度逻辑（见下）
   └─ 5. assign_tasks()      # 分配给催收员
```

#### 4.2.2 任务生成核心逻辑

```python
def generate_tasks(today: date, batch_id: str):
    config = get_active_risk_config()
    # 查所有未支付订单
    unpaid_orders = get_unpaid_orders()
    
    for order in unpaid_orders:
        tier = order.risk_tier
        schedules = get_schedules(config.id, tier)  # 该档所有催收时点
        
        for sch in schedules:
            due_date = order.win_bid_date + timedelta(days=sch.day_offset)
            
            # 命中条件：应催日 <= 今日 且 该时点未生成过任务（幂等）
            if due_date <= today:
                # 幂等检查：同 order + 同 day_offset 不重复
                if not task_exists(order.id, sch.day_offset, batch_id):
                    # 二次确认：当前仍未支付才生成
                    if order.pay_status != 'PAID':
                        create_task(order, sch, due_date, batch_id)
```

> **幂等设计**：`batch_id`（日期）+ `order_id` + `day_offset` 三元组唯一约束，防止重复生成。

#### 4.2.3 任务分配算法

```python
def assign_tasks(today_tasks: list[Task]):
    # 按风险档排序：HIGH > MEDIUM > LOW；同档按账龄倒序
    sorted_tasks = sort_by_priority(today_tasks)
    
    collectors = get_active_collectors()  # 3 名
    # 负载均衡：轮询分配，但保证高风险优先给当前负载最低的人
    loads = {c.id: get_pending_count(c.id) for c in collectors}
    
    for task in sorted_tasks:
        assignee = min(loads, key=loads.get)  # 当前负载最低者
        task.assignee_id = assignee
        task.status = 'PENDING'
        loads[assignee] += 1
```

#### 4.3.2 模板匹配逻辑

```python
def match_template(task, order, features) -> list[TalkTemplate]:
    age = (today - order.win_bid_date).days
    age_bucket = map_age_bucket(age)  # 0_7 / 8_15 / ...
    
    # 匹配优先级：精确档×精确段×精确场景×特征 > 逐级放宽(ANY)
```

```python
# 生成 Prompt 组装
def build_prompt(order, features, task, template_hint):
```

## 7. AI 功能架构（基于 agent-app-builder 方法论）

本系统含两类 AI 能力，遵循"抽象 Provider + 可替换 + 可降级"原则：

### 7.1 AI 能力清单

| 能力 | 类型 | MVP 实现 | 后续演进 |
|------|------|---------|---------|
| 风险概率预测 | 预测模型 | Mock Provider（规则加权） | Algorithm Provider（训练好的分类模型） |
| 智能话术生成 | LLM 生成 | Mock 或真实 LLM（可开关） | 真实 Claude/OpenAI，基于反馈优化 |

### 7.2 控制分配（Control Allocation）考虑

| 决策点 | 控制方 | 说明 |
|--------|--------|------|
| 是否调用 AI 生成话术 | 系统+人 | 系统按维度推荐模板；催收员可主动触发 AI 生成/润色 |
| AI 生成内容是否采用 | 人 | 催收员决定采用哪段话术，并标记反馈 |
| 风险档阈值调整 | 人（主管） | 管理员配置，系统不自动改阈值 |
| 任务分配 | 系统 | 系统按规则分配，主管可手动改派 |

### 7.3 失败与降级

| 场景 | 降级策略 |
|------|---------|
| LLM 调用超时/失败 | 返回模板话术，记录失败，不影响催收 |
| 风险算法服务不可用 | 使用上次缓存风险概率，标记 stale |
| 跑批失败 | 重试 3 次，失败告警，不影响历史任务 |

### 7.4 工具设计（Tool Design）

- 话术生成的 LLM 仅做"文本生成"单一职责，不赋予调用业务系统/改数据的工具（避免误操作）。
- 风险算法仅做"概率计算"，不直接生成任务（任务生成由确定性 task_engine 负责）。

## 8. 部署架构

```
┌─────────────────────────────────────┐
│         Docker Compose              │
│  ┌──────────┐  ┌────────────────┐   │
│  │ frontend │  │   backend      │   │
│  │  (nginx)  │  │  (FastAPI+uv)  │   │
│  └─────┬────┘  └───────┬────────┘   │
│        │               │            │
│        └───────┬───────┘            │
│           ┌────▼─────┐              │
│           │ postgres │              │
│           └──────────┘              │
└─────────────────────────────────────┘
```

- 前端构建静态资源由 nginx 托管，反代 `/api` 到后端。
- 后端单进程 + APScheduler（进程内调度）。
- 开发期可 SQLite，生产用 PostgreSQL。
